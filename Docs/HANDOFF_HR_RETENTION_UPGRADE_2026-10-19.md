# HR 퇴사 위험 분석 플러그인 고도화 핸드오프

작성일: 2026-10-19 (Asia/Seoul)

상태: **설계·구현 인계 문서. 아래 개선은 아직 구현하지 않았다.**

대상: `hr_attrition_plugin`, 주 사용자는 Claude Chat/Cowork에서 Excel로 업무를 수행하는 HR 실무자.

## 1. 목표와 첫 출시 범위

목표 경험은 “우리 회사 엑셀을 이해하고, 지난번과 달라진 문제를 찾아, 원본 근거와 확인할 일을 함께 제공하며, 다음 달에도 맥락을 이어가는 것”이다.

첫 고도화 출시의 대표 기능은 **전월 대비 조직 변화 + 원본 근거 + HR 확인사항**이다. 실제 퇴사 라벨 없이도 이 기능을 제공한다. 예측 모델은 별도의 데이터·검증 조건을 충족할 때 활성화한다.

첫 출시에서 완료할 범위:

1. 잘못된 검증 통과·설정 재현·버전 불일치를 수정한다.
2. 엑셀 입력의 기준일·사번·단위·중복·기간을 검사하고 근거를 추적한다.
3. 두 시점의 동일 재직자 변화와 인원 구성 변화를 구분한다.
4. 4개 업무 시트와 간결한 대화 응답을 제공한다.
5. HR 확인·조치 기록을 다음 실행으로 이어받는다.

실제 과거 라벨로 검증한 예측 모델, 조치의 인과 효과 추정, 실시간 HRIS 연동, 자동 메일·인사 조치는 첫 출시의 필수 조건이 아니다. 모델을 사용할 수 없어도 데이터 진단·변화 분석은 독립적으로 완료한다.

| `report.py`, `dashboard.py` | Excel의 `_data`/`_meta`로 대시보드 연결 | 기존 결과 파일 호환성을 고려하며 출력 변경 필요 |

기존 `artifacts/it_platform/metrics.json`은 규칙 모드다. 기존 산출물을 신규 코드의 검증 결과로 취급하지 않는다.

이번 대화의 테스트 시도는 완료되지 않았다. 기본 `python.exe` 실행이 실패했고, 발견한 번들 Python에는 `pytest`가 없었다. 따라서 테스트 통과·실제 Claude 환경 동작·실제 HR 데이터 성능은 확인되지 않았다. 문서 작성 시 해당 폴더는 Git 저장소로 인식되지 않았으므로 기준 커밋도 기록하지 못했다.

## 3. 구현 기본 결정

후속 구현자는 아래를 기본값으로 사용한다. 새로운 임계값·모델 정책을 추가하면 설정과 검증 근거를 함께 기록한다.

- **분석 모드:** `diagnostic`(현재 상태), `change`(시점 비교), `predictive`(검증된 기간별 예측)를 제품 수준에서 구분한다. 기존 CLI의 `heuristic/model/auto`는 계산 방식이므로 별도 필드로 유지하거나 명시적으로 마이그레이션한다.
- **질문 표현:** 진단 모드에서는 “90일 내 퇴사 예측”으로 출력하지 않는다. 요청한 질문과 현재 데이터로 답할 수 있는 질문을 각각 기록한다.
- **수치 책임:** Python 엔진이 계산하고 Claude는 구조화된 결과를 설명한다. 대화에서 가중치·수치·근거를 임의로 만들어 채우지 않는다.
- **필터:** 기준 모집단을 정하는 설정과 이미 계산한 결과를 좁혀 보는 표시 필터를 구분한다. 후속 “이 팀만” 요청은 기본적으로 표시 필터다.
- **기준일:** 파일의 명시적 기준일 또는 사용자가 지정한 기준일을 사용한다. 충돌·누락은 확인 필요로 반환한다. 오늘 날짜를 과거 파일에 조용히 적용하지 않는다.
- **식별자:** 파일 내 임시 ID는 단면 분석에서만 허용한다. 시점·파일 간 연결은 검증된 안정적 직원 ID 또는 명시적 매핑을 요구한다. 이름만으로 자동 병합하지 않는다.
- **데이터 부족:** 근거 부족은 `insufficient_evidence`로 표시한다. 결측을 위험 없음으로 해석하지 않는다.
- **민감 정보:** 성별·국적 등 기존 제외 속성의 예측 입력 경로를 닫는다. 병가와 설문 미응답은 기본 개인 위험 가중치에서 제거한다. 건강·휴직·자유서술에서 개인 성향을 추론하지 않는다. 허용 피처 목록을 엔진에서 강제한다.
- **공유 범위:** 기본 답변은 조직 단위, 개인 상세는 업무상 필요한 요청 범위로 제한한다. 기본 소집단 표시 기준은 5명으로 설정 가능하게 두되, 이 값 자체가 익명성을 보장하지는 않는다고 명시한다.
- **산출물 보존:** 입력 파일을 수정하지 않는다. 실행별 출력 폴더를 사용하고 이전 결과·HR 확인 기록을 보존한다.
- **시나리오:** 급여·업무량 입력 변경에 따른 점수 변화와 실제 퇴사 감소 효과를 구분한다. 인과 검증 전에는 방지 인원·ROI를 확정적으로 제시하지 않는다.

P0 단계에서는 기능을 넓히지 않고 기존 표준 워크북·단일 명부·대시보드 연결 회귀를 확인한다.

### P1 — 실제 엑셀 수용력과 원본 근거

기존 `data.py`를 진입점으로 유지하면서 아래 책임을 분리한다. 새 파일명은 제안이며 기존 인터페이스에 맞춰 조정할 수 있다.

- `ingestion.py`: 시트 후보 탐색, 헤더 위치·표 범위·수식 캐시 상태 수집, 다중 파일 로드.
- `mapping.py`: 표준 필드 매핑·단위·날짜 형식과 회사별 매핑 저장. 기존 별칭을 초기 규칙으로 재사용.
- `quality.py`: ID 중복·조인 미일치·기준일 충돌·날짜 해석 실패·급여 단위·불가능한 값 검사.
- `evidence.py`: 변환 전 원본 위치와 변환 규칙을 보존하고 집계 근거를 연결.

자동으로 확정할 수 없는 급여 단위, 중복 컬럼 의미, 서로 다른 기준일은 추정 확정하지 않는다. Claude가 한 번에 필요한 확인사항만 묻도록 `questions[]`를 반환한다. 나머지 검사는 먼저 완료한다. 확인한 매핑은 다음 실행에서 재사용하되 새 파일의 스키마 변화는 재검사한다.

수식 셀은 값의 최신성을 구분한다. 재계산 가능한 환경에서 검증하거나, 캐시가 없거나 신뢰할 수 없으면 해당 신호를 평가 불가로 표시한다. 파일의 메모·셀 텍스트는 데이터로 처리하며 실행 지시로 사용하지 않는다.

완료 조건:

1. 헤더가 첫 행이 아닌 파일, `000123` 사번, 원/만원 혼용, 월급/연봉 혼동, 중복 사번, 시트명 변경을 구분해서 처리한다.
2. 연봉 환산은 급여 주기·단위를 명시한 매핑에만 적용한다. 이름이 같은 직원은 서로 다른 ID로 유지한다.
3. 모든 출력 주장에 근거 ID가 있고, 원본 파일·시트·행/셀 또는 집계 대상 행 목록으로 역추적할 수 있다.
4. 입력 정렬이 바뀌어도 ID 기반 조인 결과가 같고, 원본 위치는 각 실행의 파일에 맞게 갱신된다.
5. 입력에 문제가 있으면 영향을 받는 분석만 보류하고 가능한 진단은 반환한다.

### P2 — 월별 변화와 비교 기준 고정

수정/추가 대상: `features.py`, `model.py`, `question.py`, `overview.py`, `snapshots.py`, `comparison.py`, `reference.py`.

우선 두 개의 날짜가 명시된 스냅샷을 입력받아 비교한다. 현재 명부만으로 과거 소속·보상·재직 상태를 복원했다고 주장하지 않는다.

계산할 변화:

- 동일 직원의 동일 지표 변화와 관측 기간·커버리지 변화.
- 팀 전체 집계 변화 및 동일 소속 유지 직원의 변화.
- 입사·퇴사·이동에 따른 구성 변화. 매칭되지 않은 사람은 별도 건수로 표시.
- 신호의 신규 발생·지속·해소. 반복 계산에서는 같은 이슈가 중복 생성되지 않도록 안정적 키 사용.

조직 ID 또는 확인된 조직 매핑을 사용한다. 팀명 변경과 실질 조직 이동을 구분한다. 동일 재직자 집계가 전체 조직의 변화를 대표하지 않을 수 있으므로 이탈·유입 인원도 함께 보여준다.

점수 비교가 필요한 경우 표준화·결측 처리·가중치·밴드 기준을 기준 버전에 고정한다. 비교 기준을 재학습하면 새 버전을 부여한다. 다른 버전 점수는 그대로 차감하지 않고 공통 버전으로 재계산하거나 비교 불가로 표시한다. 원시 지표 변화는 점수와 별도로 제공한다.

완료 조건:

1. 데이터가 동일하고 표시 필터만 바뀌면 직원 점수와 근거가 바뀌지 않는다.
2. 팀에 저근속 직원이 유입되어 평균 근속이 하락한 사례를 기존 직원의 근속 악화로 설명하지 않는다.
3. 팀명 변경·직원 이동·누락 파일을 실제 업무량 변화와 구분한다.
4. 두 시점의 단위·관측 기간·기준 버전이 다르면 그대로 변화율을 제시하지 않는다.
5. 이력 없는 입력은 진단 모드로 완료하고 시점 비교 불가 이유를 표시한다.

### P3 — 업무용 Excel과 Claude 대화

수정 대상: `report.py`, `dashboard.py`, 두 스킬의 `SKILL.md`와 reference, `cli.py`. 계산·집계는 공통 엔진을 사용한다.

기본 업무 시트:

| 시트 | 필수 내용 |
|---|---|
| 이번 달 요약 | 관측된 주요 변화 최대 3개, 분석 범위·기준일, 확인 필요 사항, 데이터 제약 |
| 조직별 변화 | 두 시점 값·차이·분모·매칭 인원·구성 변화·소집단 억제 상태 |
| 근거 상세 | 주장 ID, 값·기간·단위·비교 기준·출처, 반대 근거, 근거 부족 이유 |
| 실행 관리 | 이슈 ID, HR 확인 질문, 담당자, 기한, 상태, 확인된 맥락, 후속 점검일 |

기술적 검증은 부록으로 유지한다. 기존 결과의 `_data`/`_meta` 읽기를 지원하거나 명시적인 변환 경로를 제공한다. 새 결과 형식에는 스키마 버전을 넣는다.

공유용과 HR 상세용 출력을 분리한다. 공유용은 개인 행·이름·자유서술을 실제로 제거하며 숨김 시트에 남겨 두지 않는다. HTML 대시보드의 내장 JSON도 같은 정책을 적용한다.

대화 흐름:

1. 최초 파일 입력: 데이터 준비 상태와 답할 수 있는 범위를 먼저 확인한다.
2. 최초 결과: 핵심 발견, 근거, 확인할 일, 파일 링크를 짧게 전달한다. 6단계 상세는 요청 시 펼친다.
3. “왜?”: 해당 주장·근거 ID만 조회하여 원본 값과 반대 근거를 제시한다.
4. “이 팀만”: 저장 결과에 표시 필터를 적용한다.
5. “지난달과 비교”: 파일·기준 버전·조직 매핑을 확인하고 비교 엔진을 실행한다.
6. “이 신호를 제외하면?”: 별도 시나리오 실행을 만들고 원래 결과를 보존한다. 점수 변화와 실제 효과를 구분한다.

환경별 연결:

- Chat: 첨부 파일을 읽고 다운로드 가능한 결과 Excel과 다음 실행에 필요한 상태 파일을 제공한다. 대화 기억만으로 이력을 보존하지 않는다.
- Cowork: 사용자가 지정한 작업 폴더에서 실행별 결과와 상태를 읽고 쓴다. 다른 회사의 상태를 자동 혼합하지 않는다.
- Excel 애드인: 열린 파일·시트의 읽기/쓰기 도구와 커스텀 스킬의 실행 가능 범위를 실제 환경에서 확인한 후 별도 연결부를 만든다. Python 파일 처리 경로와 동일하다고 가정하지 않는다.

완료 조건: 채팅·Excel·HTML의 같은 주장은 같은 계산값과 근거 ID를 사용한다. 근거가 없는 문장을 제외하고, 기존 결과만으로 가능한 질의는 분석을 재학습하지 않는다. 배포 환경에서 차트 외부 리소스가 막혀도 표와 핵심 결과는 읽을 수 있다.

### P4 — 다음 달에도 이어지는 실행 기록

추가 대상: `actions.py`, `state.py`, Excel 실행 관리 시트 가져오기/내보내기.

상태는 `open/in_progress/done/deferred` 등 유한한 값으로 관리한다. 조치에는 안정적 `action_id`와 생성 실행 ID를 둔다. 사용자 편집 셀과 계산 셀을 구분한다.

HR 확인 기록은 `이슈 ID, 작성자, 작성 시각, 사실 확인/가설/조치 구분, 내용, 출처`를 저장한다. “프로젝트 마감 영향” 같은 코멘트를 실제 퇴사 라벨이나 점수 보정값으로 자동 사용하지 않는다. 모델과 반대되는 의견도 근거와 함께 보존한다.

완료 조건:

1. 사용자가 Excel에서 입력한 담당자·기한·상태가 다음 실행에도 유지된다.
2. 같은 파일을 다시 가져와도 조치가 중복 생성되지 않는다.
3. 같은 항목의 동시 변경은 조용히 덮어쓰지 않고 충돌로 반환한다.
4. 조치 후 지표 변화는 관측 결과로 기록하며 조치가 원인이라고 단정하지 않는다.

### P5 — 실제 데이터에 근거한 예측 모드

P0~P4 출시를 기다리게 하지 않는 별도 작업이다. 실제 이력 데이터가 없으면 합성 fixture로 처리 경로만 검증하고 출시 성능은 미검증으로 남긴다.

수정/추가 대상: `labels.py`, `model.py`, `validation.py`, `training.py`, `evaluation.py`.

필요한 학습 데이터:

- 기준일 당시 재직 대상자의 과거 스냅샷과 당시 사용 가능했던 신호.
- 실제 퇴사일·퇴사 유형·결과 관측 종료일.
- 직원 ID, 기준일, 필요하면 고용 에피소드 ID. 재입사·계약 만료를 명확히 처리.

라벨 정의: 기준일 이후 지정 기간 안의 대상 퇴사는 양성, 해당 기간 전체 관측 후 대상 사건이 없으면 음성. 관측 미완료·경쟁 사건·유형 불명은 정책에 따라 제외 또는 별도 모델링하며 음성으로 일괄 처리하지 않는다. 이미 퇴사한 사람의 현재 상태를 과거 예측 입력에 섞지 않는다.

평가 설계:

1. 과거 학습·이후 검증·최종 미래 평가 구간을 분리하고 라벨 성숙 기간을 확보한다. 겹치는 라벨 기간은 경계에서 제거 또는 시간 간격을 둔다.
2. 직원 반복 관측의 의존성을 고려한다. 기존 직원의 다음 달 예측과 새 직원 일반화를 별도 평가하며 직원 ID는 모델 피처로 넣지 않는다.
3. 결측 대치·표준화·피처 선택·확률 보정은 평가 구간을 보지 않고 학습 구간에서 결정한다.
4. 단순 기준선과 로지스틱 회귀부터 비교한다. 복잡한 모델은 같은 미래 평가에서 개선될 때 채택한다.
5. PR-AUC, ROC-AUC, 월 처리 가능 인원 K에서 precision/recall/lift, 확률 보정, 기간별 변동·불확실성을 보고한다.
6. 예측 실패·데이터 분포 변화·표본 부족 시 진단 모드로 내려가고 이유를 남긴다.

출시 조건은 파일럿 시작 전에 HR의 처리 용량 K와 오경보 허용 수준을 정해 기록한다. 양성 10명 또는 임의 AUC 하나로 출시 승인하지 않는다. 실제 미래 구간에서 기준선 대비 유용성·확률 품질·주요 집단의 오류 편차를 확인한다. 집단별 성능 감사에 필요한 정보는 예측 입력과 분리된 승인 범위에서만 다룬다.

## 5. 공통 데이터 계약 제안

아래는 신규 구현 제안이며 현재 존재하는 API가 아니다. P0에서 스키마를 작게 정의하고 각 단계에서 확장한다.

| 객체 | 최소 필드 | 지켜야 할 성질 |
|---|---|---|
| `AnalysisSpec` | schema_version, company_id, question, as_of, mode, population, feature_policy, reference_id, parameters | 질문·기준 모집단·계산 설정의 재현 가능한 원천 |
| `RunManifest` | run_id, input_hashes, source_ids, engine_version, spec_hash, executed_at, warnings | 입력·설정·실행을 연결. 해시는 개인정보 익명화 수단이 아님 |
| `QualityIssue` | code, severity, affected_fields, source_refs, blocking_capabilities, resolution | 어떤 분석을 왜 막는지 기계적으로 판단 가능 |
| `Evidence` | evidence_id, source_refs, metric, value, unit, period, population, transform, missingness | 원본 사실과 파생 지표를 구분하고 계산을 추적 가능 |
| `Finding` | finding_id, observation, evidence_ids, comparison, alternative_explanations, evidence_status | 관측·해석·확인 필요 사항을 분리. 근거 없는 정량 확신도 금지 |
| `Reference` | reference_id, feature_schema, fit_period, imputation, scaling, weights_or_model, bands | 필터·월별 실행에서 비교 기준을 고정 |
| `Action` | action_id, finding_id, owner, due_date, status, notes, updated_at | 재실행 때 사용자 입력 보존, 위험 점수와 별도 관리 |

원본 참조는 `source_id + 파일 해시 + sheet + 원본 행/셀 + 직원 ID(해당 시)`를 포함한다. 대규모 집계는 원본 행 목록을 별도 파일에 두고 참조한다. 행 번호만으로 직원 정체성을 결정하지 않는다.

상태 폴더 예시:

```text
<사용자가 지정한 작업 폴더>/
  company_config.json
  analysis_spec.json
  state/
    references/
    snapshots/
    actions.json
  runs/<run_id>/
    run_manifest.json
    summary.json
    evidence.json
    HR_분석결과.xlsx
```

폴더 구조는 구현 시 조정 가능하되 회사 분리·실행별 보존·사용자 기록 보존은 유지한다. 임시 파일도 개인정보를 포함할 수 있으므로 배포 패키지에 포함하지 않는다.

## 6. 검증과 배포 인계

기존 `tests/test_pipeline.py`는 회귀 기준으로 유지한다. 신규 테스트는 다음 실패 상황과 업무 계약을 확인하는 데 집중한다.

| 검증 묶음 | 대표 사례 | 완료 단계 |
|---|---|---|
| 입력 | 기준일 없음/충돌, 중복·선행 0 사번, 단위 혼용, 날짜 오류, 수식 캐시 없음 | P0~P1 |
| 재현 | 스펙 복원, CLI override, 엔진 버전 불일치, 입력 순서 변경 | P0 |
| 근거 | 집계 수치를 원본으로 재계산, 변환된 값의 출처 추적 | P1 |
| 비교 | 표시 필터 불변성, 팀명 변경, 입퇴사/이동, 기간·모델 기준 불일치 | P2 |
| 보고 | 채팅 입력 JSON·Excel·HTML 수치 일치, 공유 결과의 개인 데이터 제거 | P3 |
| 이력 | 반복 import, 사용자 메모 보존, 변경 충돌, 회사 상태 혼합 방지 | P4 |
| 모델 | 미성숙 라벨, 미래 정보 유입, 무작위 분할 대신 시간 평가, 보정·기준선 비교 | P5 |

검증 환경부터 복구한다. 사용할 Python 실행 파일을 확인하고, 프로젝트 개발 의존성을 갖춘 환경에서 기존 테스트를 실행한다. 아래는 프로젝트 루트에서 사용할 명령이며 이번 문서 작성에서 성공 실행한 명령이 아니다.

```powershell
python -m pip install -e ".[dev]"
python -m pytest tests -q
python make_skill_zip.py
```

배포 시 두 ZIP을 별도 임시 폴더에 풀고 저장소의 `engine` 경로 없이 각각 실행한다. 두 ZIP의 엔진 파일·버전 일치와 불필요한 실제 HR 파일 미포함을 검사한다. 단일 명부·표준 워크북·결과 파일만으로 대시보드 생성하는 경로를 확인한다.

Claude Chat/Cowork의 실제 설치·실행 검증은 로컬 Python 테스트와 구분해서 기록한다. 파일 생성, 후속 근거 질의, 두 시점 비교, HR 편집값 재사용을 직접 확인하고 접근할 수 없으면 해당 환경은 미검증으로 남긴다.

## 7. 다음 구현자가 바로 시작할 작업

1. 현재 파일과 실행 환경을 다시 확인하고 기존 테스트 기준선을 확보한다. 사용자 기존 산출물은 덮어쓰지 않는다.
2. P0-1~P0-3을 하나의 작은 변경 단위로 구현한다. 입력 오류·날짜 미확인·민감 피처 유입이 실제로 구분되는지 검증한다.
3. P0-4~P0-6에서 스펙·버전·표현을 일치시키고 같은 설정의 재실행 결과를 비교한다.
4. P1의 최소 범위로 “단일 명부의 원본 위치 → 신호 → 보고서 근거”를 끝까지 연결한다. 이후 다중 파일로 확장한다.
5. P2~P4를 거쳐 가상의 두 달 파일과 HR 수정 기록으로 대표 시나리오를 시연한다.
6. 실제 파일럿 데이터가 확보된 뒤 P5의 라벨 정의와 평가 구간을 확정한다.

첫 고도화 출시의 완료 기준: **HR 담당자가 자기 엑셀을 입력하고, 주요 발견의 원본을 확인하고, 확인사항을 수정한 뒤, 다음 달 파일에서 그 맥락을 이어갈 수 있다.** 예측 모델 성능은 이 기준과 별도의 증거로 관리한다.
